# 钉钉提醒机制说明

> 面向复用：本文档完整描述宿舍管理系统的钉钉到期提醒实现，供其他系统（如刀具管理系统，Node + Express + SQLite）移植参考。
>
> 更新日期：2026-09-18 · 对应版本 v0.8

---

## 1. 整体架构

钉钉提醒由 5 个彼此独立的部分组成，可分别移植：

```
钉钉开放平台（企业内部应用）
    │  4 个凭证参数
    ▼
[A] 钉钉 API 封装 ──── 获取 access_token（缓存 ~2 小时）
    │                  发送工作通知 asyncsend_v2
    │                  免登换 userid（可选，仅用于自动绑定）
    ▼
[B] 接收人管理 ──── users 表: dingtalk_userid + receive_xxx_reminders 开关
    ▼
[C] 调度器 ──── 应用内后台线程，每 30 分钟扫一次，当地时间 9 点后才发
    ▼
[D] 提醒规则 ──── 到期项 × 提前档位（30/15/7/0 天），每次只发最贴近的档位
    ▼
[E] 幂等台账 ──── 唯一键含"目标到期日"，同一到期日同一档位只发一次
```

本仓库对应源码：

| 部分 | 文件 |
| --- | --- |
| [A] API 封装 | `backend/services/dingtalk.py`（107 行，纯 Python 标准库，无第三方依赖，可整体照抄） |
| [B] 接收人 | `backend/models/entities.py` User 表：`dingtalk_userid`、`receive_bill_reminders`、`receive_vehicle_reminders` |
| [C] 调度器 | `backend/app.py` `_utility_bill_reminder_loop` |
| [D]+[E] 规则与幂等 | `backend/services/management.py`：`run_vehicle_reminders`（第二代，推荐）、`run_utility_bill_reminders`（第一代） |
| 免登前端 | `frontend/src/pages/LoginPage.tsx`（dingtalk-jsapi `requestAuthCode`） |

## 2. 钉钉开放平台前置配置（一次性）

在 open.dingtalk.com 创建**企业内部应用**（H5 微应用），获取 4 个参数：

| 参数 | 环境变量 | 用途 |
| --- | --- | --- |
| Client ID（AppKey） | `DINGTALK_CLIENT_ID` | 换 access_token |
| Client Secret（AppSecret） | `DINGTALK_CLIENT_SECRET` | 换 access_token |
| CorpId | `DINGTALK_CORP_ID` | 前端免登 JSAPI 用 |
| **AgentId** | `DINGTALK_AGENT_ID` | **发工作通知必需**，在应用"基础信息"页 |

应用后台还需配置：

- **服务器出口 IP 白名单**：调服务端 API 的机器出口 IP 必须加入，否则 gettoken / asyncsend 直接报错。
- **权限**：发本应用工作通知默认可用；按 userid 查姓名（`topapi/v2/user/get`）需申请"通讯录个人信息读权限"。

**多系统可以复用同一个应用的 4 个参数**（消息落款区分系统即可）；希望钉钉里显示不同应用名/图标时再另建应用。凭证放环境变量或 `.env`，**绝不进 git**。

## 3. 三个钉钉 API

### 3.1 获取 access_token

```
GET https://oapi.dingtalk.com/gettoken?appkey=...&appsecret=...
→ {"errcode":0, "access_token":"...", "expires_in":7200}
```

**必须缓存**（进程内存即可），过期前 60 秒刷新；每次调用都取会被频控。见 `dingtalk.py` 的 `_token_cache` / `_get_access_token()`。

### 3.2 发送工作通知（核心）

```
POST https://oapi.dingtalk.com/topapi/message/corpconversation/asyncsend_v2?access_token=...
{
  "agent_id": "<AgentId>",
  "userid_list": "userid1,userid2",
  "msg": {"msgtype": "text", "text": {"content": "【车辆到期提醒】...\n请及时处理。"}}
}
→ {"errcode":0, "task_id": ...}   （异步投递）
```

**两个踩坑点：**

1. **钉钉自身有内容去重**：同一应用对同一用户，一天内完全相同的内容只有第一条生效。消息模板里务必带会变化的字段（日期、"N 天后到期"等）。
2. 频控约每分钟 500 次调用，`userid_list` 单次最多 100 人 —— 应把多条提醒**聚合成一条消息**发（本系统即如此），而不是一项一条。

### 3.3 免登换 userid（可选）

前端在钉钉容器内：

```ts
const dd = (await import("dingtalk-jsapi")).default;
const { code } = await dd.runtime.permission.requestAuthCode({ corpId });
// POST 给后端 /api/auth/dingtalk-login
```

后端：`POST topapi/v2/user/getuserinfo {code}` → `userid`；再 `POST topapi/v2/user/get {userid}` → 姓名。

这只是获取 userid 最省事的方式。**新系统不做免登也完全可行**：管理员在钉钉管理后台查每个人的 userid 手工录入即可。

## 4. 接收人管理

`users` 表两个字段：

- `dingtalk_userid`：绑定钉钉账号（免登自动写入，或手工维护）
- `receive_vehicle_reminders` / `receive_bill_reminders`：布尔开关，管理页勾选

发送时取"开关开 **且** userid 非空"的用户。**不同业务用独立开关**——不同提醒的受众通常不是同一批人，共用一个开关会互相打扰。

## 5. 调度器

应用启动时起一个 daemon 线程：`while True: 执行提醒 → sleep(30 分钟)`。要点：

- 循环体整体 try/except，**任何异常只记日志不退出**，保证调度器长活；
- 发送函数自己判断"当地时间 9 点前不发"（`respect_send_hour` 参数），轮询间隔无需对齐 9 点——9 点后的第一次轮询自然会发；
- **时区**：服务器可能是 UTC，"今天/几点"必须用业务时区算（本系统 `APP_TIMEZONE` + `backend/core/clock.py` 的 `local_today()/local_now()`）；
- 另暴露两个手动端点：`POST .../reminders/run`（跳过 9 点门限立即执行，排查用）、`POST .../reminders/test`（发测试消息验证链路）。

## 6. 提醒规则：档位算法

每类到期项配一组提前档位，**0 表示"已过期后再提醒一次"**：

```python
VEHICLE_REMINDER_STAGES = {
    "insurance_expire":    [30, 15, 7, 0],
    "inspection_expire":   [30, 7, 0],
    "registration_expire": [30, 7, 0],
    "maintenance_due":     [15, 0],
    "lease_expire":        [60, 30, 0],
    "license_expire":      [30, 7, 0],
}
```

每次轮询，对每个到期项：

```
days_left  = 到期日 − 今天
applicable = [s for s in stages if days_left <= s]   # 已进入哪些档位
若 applicable 为空 → 还太早，跳过
stage = min(applicable)                              # ★ 只取最贴近的一档
若台账已有 (实体, 提醒类型, stage, 到期日) → 跳过
否则 → 加入本次消息，发送成功后写台账
```

`min(applicable)` 解决两个问题：录入时就只剩 5 天的项只发 7 天档一条，**不会 30/15/7 三档一次性轰炸**；正常推进时 30→15→7→过期各提醒一次。

循环类提醒（如"理赔超 30 天未结案每 30 天一次"）：用期数 k 作档位、`起算日 + 30k 天` 作目标日期，每期一行台账。

## 7. 幂等台账（最重要的设计）

本系统迭代过两代方案：

- **第一代（水电账单）**：业务表加 `reminded_on` 字段，发过填日期，改到期日时清空重新武装。只适合"一个实体一种提醒只发一次"的简单场景。
- **第二代（车辆，移植请用这个）**：独立台账表——

```sql
CREATE TABLE reminder_logs (
  id              INTEGER PRIMARY KEY,
  entity_type     VARCHAR(40) NOT NULL,   -- 业务实体类型
  entity_id       INTEGER     NOT NULL,
  remind_kind     VARCHAR(40) NOT NULL,   -- 提醒种类
  remind_stage    INTEGER     NOT NULL,   -- 档位(30/15/7/0 或循环期数)
  due_target_date DATE        NOT NULL,   -- 本次提醒针对的到期日  ★关键
  reminded_on     DATE        NOT NULL,
  UNIQUE (entity_type, entity_id, remind_kind, remind_stage, due_target_date)
);
```

**唯一键必须包含 `due_target_date`**：到期日一变（如完成续保后日期更新），新日期 = 新记录，自动对新日期重新按档位提醒，无需任何"清标记"逻辑；旧日期的记录留作发送历史。（本系统设计评审时曾漏掉这一列，会导致"续期后永远不再提醒"，务必带上。）

**发送与写台账的顺序**：先检查配置与接收人，**发送成功后才写台账并提交**。钉钉未配置或发送失败时不消耗幂等记录，下次轮询自动重试，不丢提醒。

## 8. 消息拼装规范

- 一次轮询的所有到期项聚合为**一条**文本消息（标题 + 逐行明细 + 结尾动作句）：

```
【车辆到期提醒】以下事项需要处理：
· ABC-1234（1号宿舍）保险到期：2026-09-15（22 天后到期）
· XYZ-8899（2号宿舍）保养到期：2026-08-30（13 天后到期），48,200 / 50,000 mi
请及时处理。
```

- 每行带实体标识 + 到期日 + 剩余/逾期天数；已过期写"已过期 N 天"、当天写"今天到期"；
- 标题用【系统/业务名】前缀，多系统共用一个钉钉应用时靠它区分来源。

## 9. Node/Express + SQLite 移植要点

```js
// dingtalk.js —— 对应本仓库 backend/services/dingtalk.py
let tokenCache = { token: null, expiresAt: 0 };

async function getAccessToken() {
  if (tokenCache.token && tokenCache.expiresAt > Date.now() + 60_000) return tokenCache.token;
  const res = await fetch(
    `https://oapi.dingtalk.com/gettoken?appkey=${APPKEY}&appsecret=${APPSECRET}`
  ).then(r => r.json());
  if (res.errcode !== 0) throw new Error(`钉钉获取凭证失败: ${res.errmsg}`);
  tokenCache = { token: res.access_token, expiresAt: Date.now() + res.expires_in * 1000 };
  return res.access_token;
}

async function sendWorkMessage(userids, content) {
  const token = await getAccessToken();
  const res = await fetch(
    `https://oapi.dingtalk.com/topapi/message/corpconversation/asyncsend_v2?access_token=${encodeURIComponent(token)}`,
    {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({
        agent_id: AGENT_ID,
        userid_list: userids.join(","),
        msg: { msgtype: "text", text: { content } },
      }),
    }
  ).then(r => r.json());
  if (res.errcode !== 0) throw new Error(`钉钉消息发送失败: ${res.errmsg}`);
  return res.task_id;
}
```

- 调度器：`setInterval(runReminders, 30 * 60 * 1000)` 或 node-cron，回调整体 try/catch；9 点门限用业务时区判断（如 dayjs `tz("America/New_York").hour()`）。
- 台账表：第 7 节 DDL 直接可用于 SQLite；用 `INSERT OR IGNORE` 配合唯一键做幂等（受影响行数为 0 = 已发过）。
- 接收人：users 表加 `dingtalk_userid TEXT` + `receive_xxx_reminders INTEGER DEFAULT 0`；不做免登则 userid 手工维护。
- 复用宿舍系统的应用凭证时，把新系统服务器的出口 IP 也加入钉钉后台白名单（同一内网出口通常已覆盖）。

## 10. 测试与排查清单

1. 配置自检分两级：`is_configured()`（3 个凭证，够免登）、`can_send_messages()`（再加 AgentId 才能发消息）——缺哪个提示哪个。
2. 上线第一步：管理页给自己开开关 → 点"测试发送" → 钉钉收到即链路通。
3. 收不到消息的排查顺序：
   开关没开 → userid 没绑定 → 未过当地时间 9 点 → 该档位已发过（查台账）→ 钉钉内容去重（当天发过完全相同内容）→ 出口 IP 不在白名单（gettoken/asyncsend 返回非 0 errcode）。
4. 手动 run 端点返回结构化原因（`{"sent":0,"reason":"未到发送时间（每天 9 点后发送）"}` 等），排查时先调它。
